## 2.3 为什么 §17 的证据强于我的探针

| | 我的探针（`14-acceptance-probe.md`） | §17 静态 STD |
|---|---|---|
| 判据 | `grouped.sum(dim=(1,2))` | **同一条**（逐字相同） |
| 是否真稀疏前向 | ❌ 否（只算注意力统计量） | ✅ 是（`SparseDraftController`） |
| 测的是什么 | **前置条件**：最后一行注意力质量保真度 | **接受率本身**，对密集验证测 |
| 证据强度 | 代理指标 | **直接观测量** |

**当代理指标与直接观测量冲突时，直接观测量胜。**
我的探针在 K=256 时报「只保住 24.6% 的最后一行质量」，并**推测**接受率会接近 0；
实测接受率是 **0.507–1.000（均值 ≈0.81）**。**推测被否证。**

### 探针错在哪（要写清楚，不能含糊）

探针隐含了一个假设：**「只有最后一个 query 行重要」**。
`build_sparse_selection` 对全部 text 行求和（`text_len` 通常只有 15–30 个 token），
这在实践中显然够用 —— 因为 §17 的接受率很高。

**即：探针的代理指标本身构造有误，不是 STD 的判据有误。**
它把一个「多行聚合」的判据，拿去和「单行 oracle」比，
再把这个比值当成接受率的上界预测 —— 这个映射没有依据。

## 2.4 一个必须同时说清的事实：接受率**并不总是**高

`PROGRESS.md:688-698` 的 static 列**不是全都接近 1**：

```
0.507  0.541  0.663  0.796  0.831  0.850  0.966  0.966  0.983  1.000
```

- 范围 **0.507–1.000**，10 样本均值 **≈0.81**。
- 所以正确表述是：**「全 query 求和的判据在部分样本上接受率达到 0.966–1.000，
  整体均值 ≈0.81」**，而**不是**「这个判据永远接近满分」。

这仍然**足以证伪**「接受率接近 0」的推测。
