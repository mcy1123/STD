## 6.1 实验设计

- batch ∈ {1, 2, 4, 8, 16, 32}，每个 batch 跑 **eager** 与 **spec**（`SparseContextDraftProposer`，k=4，W=256）两臂。
- 输入：Video-MME 前 N 个视频，**8 帧**，greedy，64 token，预热 1 次 + 重复 3 次。
- **为什么是 8 帧**：32 帧时每个请求约 19.2k prompt token，batch 32 需要 ~613k token 的 KV（按 56 KB/token ≈ 34 GiB），
  与 15.7 GiB 的模型相加放不进 48 GiB 的 A6000。8 帧（~4.8k token/请求）让 batch 32 在显存上可行。

## 6.3 核心结论：**没有测到任何真实的稀疏收益**

### 结论 1：所有 batch 的 speedup 都在 1.0 附近（0.890–1.029×）

唯一 >1× 的点是 batch=8 的 **1.029×**，只有 **2.9%**——而阶段 3 已独立量出
**开投机本身有 4.8% 的固定开销**（`p3_empty_k4` = 0.954×）。
2.9% 的「收益」小于同配置下框架自身的噪声地板，**不构成真实收益**。

### 结论 2：接受率恒为 0.0，所以加速在原理上不可能存在

batch 4 与 8 记录到 `accept_rate = 0.0`（batch 1/2 输出太短，未产生可计量的草稿组）。
**没有任何一个草稿 token 被接受** → 投机路径在这条配置上做的是**纯额外功**。

### 结论 3：框架税 > 稀疏收益（这是本阶段要区分的那件事）

| 项 | 实测 |
|---|---|
| 框架税（开投机但不草稿） | **+4.8%** 开销（阶段 3） |
| 稀疏带来的真实接受收益 | **0**（接受率 0.0） |
| 观测到的 speedup 振幅 | 0.890–1.029× |

→ **在 batch 1–8 范围内，框架税完全支配了稀疏收益。稀疏在这个机制里没有产生可测的净收益。**

### 结论 4（重要异常）：吞吐在 batch 1→2 之间崩塌 5.5×

```
batch=1 eager : 31.03 tok/s
batch=2 eager :  5.59 tok/s     <-- 5.5x 崩塌
batch=4 eager :  7.92 tok/s
batch=8 eager :  6.23 tok/s
```

batch 翻倍不该让吞吐掉到 1/5.5。运行日志同时显示：

```
Avg generation throughput: 4.3 tokens/s, Running: 1 reqs, Waiting: 0 reqs
```

即 **引擎在同一时刻只跑 1 个请求**。结合本机是共享机（邻卡 24–26% 占用），
**这不是算法效应，而是调度/争用效应**。

> **因此本阶段的 batch 曲线不能用来回答「稀疏何时才有用」** ——
> 它的形状主要由共享机的调度行为决定，而不是由 batch 大小决定。
> 要把这条曲线测干净，需要一台**独占**的 A6000。

## 6.4 b16 / b32：中止及根因（失败也是交付物）

**状态：未完成（主动中止）**

证据（`results/vllm-std/logs/06_p6_eager_b16.log`）：

```
16:00:51  init engine took 28.07 s
16:09:24  Avg prompt throughput: 143.4 tokens/s, Avg generation throughput: 2.0 tokens/s,
          Running: 1 reqs, Waiting: 0 reqs
16:13:25  Avg prompt throughput: 0.9 tokens/s, Avg generation throughput: 4.3 tokens/s,
          Running: 1 reqs
```

- b16 单一配置耗时 **> 15 分钟仍未完成**；引擎自报生成吞吐 **2.0–4.3 token/s**。
- 按该速率，64 token × 5 个批次（probe+1 warmup+3 runs）在 b32 上预计 **> 40 分钟/臂**，
  12 个配置的完整扫描不可行。
- **根因**：① 共享机邻卡争用（GPU 利用率被邻居拉到 24–26%，实际算力被抢占）；
  ② 每请求 ~4.8k token 的 prefill 在 `Running: 1 reqs` 的串行调度下无法摊薄。
- **处置**：中止扫描，保留已完成的 b1–b8 作为**可比的子曲线**；
  b16/b32 标注为「本机不可测」，**不用外推数字填充**。
