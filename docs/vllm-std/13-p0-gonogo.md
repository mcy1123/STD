# 阶段 2：P0 go/no-go 判定

> 状态：**🟡 NO-GO（对「融合」这条工程路线）；但项目阻塞点已不在 selection 成本**
> 日期：2026-09-26
> 依据：`docs/vllm-std/12-157ms-breakdown.md`、`results/vllm-std/profile_32frame.json`

---

## 2.1 判定表（按任务书规则）

任务书的规则：

> - A 占比 < 30% → GO（融合能摊销）
> - A 占比 > 60% → NO-GO（计算密度低，不可摊销）
> - 介于两者 → 写清不确定性，交回用户

**实测 A 占比 = 98.9%** → 按规则字面：**NO-GO**。

```
variant       A_gpu    A_std   B_host     wall   A/wall
core          3.775    1.854    0.036    3.811    99.1%
core+book     3.170    0.005    0.037    3.207    98.8%
naive         2.918    0.011    0.032    2.950    98.9%   <-- 采用（最保守、最稳、对应原实现）
```

**判定：NO-GO —— 不启动阶段 3（最小融合 proposer）。**

---

## 2.2 但这个 NO-GO 的理由和规则设想的不一样（必须说清）

规则设想的因果是：**A 占比高 → 说明 selection 很重 → 融合也救不了 → 放弃**。

实测的因果是：**A 占比高 → 说明 selection 已经几乎没有 host 开销可省 → 融合无意义**；
**而它的绝对开销本来就已经达标**，根本不需要救。

两个数字同时成立，方向相反：

| 问题 | 答案 | 出处 |
|---|---|---|
| 融合能省多少？ | **≤1.1%**（B 的占比） | §2.1 表 |
| selection 绝对开销是多少？ | **81.7–105.7 ms / prompt**（28 层外推） | `A × 28` |
| 占 prefill 多少？ | **9.1% – 11.7%** | ÷ 901 ms |
| 止损线 | **10%** | P0 预定义 |

**所以：止损线被压在线上（9.1%–11.7%，横跨 10%），但这不是因为「实现差」，而是因为这就是 kernel 的真实成本。**

### 融合后的乐观 / 悲观估计（任务书要求）

| 情形 | 估计 | 依据 |
|---|---|---|
| **乐观**（完美融合，host 全消） | **81.7 ms**（9.1%） | `naive` 的 A × 28，B 全部消除 |
| **悲观**（A 取 `core` 的高方差值） | **105.7 ms**（11.7%） | `core` 的 A × 28 |
| **现实**（不融合，现状） | **82–106 ms** | 与乐观情形几乎相同 —— **因为已经没有可融合的余量** |

**结论：融合的天花板收益 ≈ 1.1%，不值得投入一个 CUDA kernel 的工程量。**

### 融合工程量粗估（任务书要求）

若仍要做，需要：把 `QK^T → 行 max → exp → 归一化 → 对 query/组头求和 → top-K` 融成一个 kernel，
涉及：① 自定义 CUDA/Triton kernel（1 个）；② vLLM 侧无改动（钩子层即可）；
③ 需要处理 `text_rows=64` 这种极小 batch 的 occupancy 问题（**64 行 × 4 KV 头，并行度极低，
这恰恰是为什么 A 已经是瓶颈而绝对时间仍不大**）。
**预期收益 ≤1.1%。不建议做。**

---

## 2.3 ⚠️ 28 层外推是外推，不是实测

必须标注：**只实测了 `layers.0`**（1 层）。`×28` 是线性外推，依据是各层 attention 形状完全相同
（同 hidden、同 head 数、同序列长度）。

**未实测**：28 层的真实总耗时。要落实它需要把钩子扩成「每层都测」，成本是再一次模型加载。
**本阶段没做，所以不给它当实测数字用。**

---

## 2.4 这个判定对项目意味着什么（最重要的部分）

**selection 成本不是 STD-on-vLLM 的阻塞点。**

- 81.7 ms / prompt，占 prefill 9.1%、占端到端（基线 5.23 s）**约 1.6%**。
- 也就是说：**即使 selection 一分钱不优化，它也已经在预算内。**

那么真正的阻塞点是什么？回到阶段 3/5 的硬数字：

| 阻塞点 | 数字 | 出处 |
|---|---|---|
| **草稿接受率恒为 0** | `accept_rate = 0.0`（所有 token 级配置、所有 k、所有窗口） | `docs/vllm-std/05-std-multitoken.md` |
| **投机路径固定框架税** | 零草稿仍 **0.954×**（慢 4.8%） | `docs/vllm-std/03-dummy-proposer.md` |
| **参考答案在平局处不稳定** | token 62 精确平局；eager-vs-eager 同样分歧 | 同上 §3.4 |

**所以：P0 的问题从「selection 贵不贵」变成了「稀疏草稿到底能不能产生非零接受率」。**
前者已答（不贵），后者是**尚未回答的真问题**，而且它**不需要融合**就能测。

## 2.5 是否进入阶段 3？

**否。** 触发条件（GO）未满足：A 占比 98.9% > 60%。

**是否进入阶段 4（转向）？** 部分 —— 但不是因为「不可摊销」，而是因为「无需摊销」。
阶段 4 的内容需要按 §2.4 重写：不是「放弃 STD 转 EAGLE-3」，
而是「**先花最小成本测接受率**，再决定转不转」。

### 给用户的决策请求

两条路，我需要你选一条：

**路 A（推荐）：做「接受率探针」，不做融合。**
用现有钩子拿到稀疏选出的 top-K 视觉位置，构造一个**最小**稀疏 draft，
只回答一个问题：**接受率是否 > 0**。成本约 1 次模型加载 + 半天。
若接受率仍为 0 → STD 在视频描述任务上确实无效，转 EAGLE-3 与负面刻画，**有据可依地止损**。
若接受率 > 0 → 才值得谈端到端。

**路 B：按规则字面直接 NO-GO，转 EAGLE-3。**
不测接受率，直接执行阶段 4。省半天，但**永远不知道 STD 的失败是在「选择」还是在「草稿」**。

**我不擅自启动阶段 3（融合），因为它已被证明最多值 1.1%。**
